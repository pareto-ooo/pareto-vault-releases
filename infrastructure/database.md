# Database standards

Rules for designing and developing database layouts, for relational and document databases. They hold for any language or ORM.

NOTE: Current document is unreviewed, but will be used as ground truth for the time being.

## All databases

- **One database per app.** Only that app connects to it. No other app, "read-only" user, BI tool, reporting script or partner integration connects to it, and no live cross-database query (such as external tables) is used operationally, no database trigger calls out to other apps, and no migration or one-off script spans two databases. Data is shared through the owning app's API or its events, and analytics reads from the analytics platform, never live from the operational database. Credentials or access is thus never shared with other apps either.
- **Identifiers are generated by the application.** By default these should be GUIDv4. The database never generates them: no `IDENTITY` or sequence columns, and no database-side GUID defaults.
- **Performance Sensitive Identifiers** When a specific table has over 1mil entries or sees high frequency inserts where fragmenting becomes a problem, a GUIDv7 is used. It needs to be converted/stored as Big Endian BINARY(16) in order to gain benefits over GUIDv4. This rule is applied based on expected volume at startup, but can always be revised later.
- **A primary key is opaque.** It means nothing, encodes nothing and is never parsed (no creation time or shard hint read out of a GUID). A primary key value is never reused after a delete, so a stale reference resolves to "gone", not to another row.
- **Audit values (created and updated, at and by) are set by the application on every save**, in UTC, with the time taken from the time provider of the application that manages the database model. Authorship is the principal's GUID, never an email or display name, because those change and spread personal data over every table.
- **Optimistic concurrency uses a concurrency token** on every aggregate that can be edited concurrently. It is its own column, never mixed into the audit columns. A conflict is reported as a 409 (`CONCURRENT_UPDATE`), translated in one central place, not per endpoint.
- **Hard delete is the default.** It keeps the schema and queries simple, reclaims space and makes erasure real. If a row can be deleted safely, delete it.
- **Soft delete is for data that normal flows never need to see.** It is justified only by an audit or regulatory duty (the row's existence at a point in time is the record), or by recoverability as a product feature. If any ordinary flow (a summary, grouping, analysis, a display) still needs the row, it is not deleted: model it as an explicit state (for example `Retracted`) instead. Default reads exclude deleted rows, and reading them is a named, intent-revealing path (restore, audit), never inline in a general query.
- **Soft delete does not cascade silently.** Dependents of a soft-deleted parent keep pointing at it. Soft-deleting dependents too is a deliberate domain choice written in the service, never in a trigger. Hard-deleting the dependents of a soft-deleted parent is always wrong.
- **Restoring a soft-deleted row is a domain operation.** It first verifies that no active row conflicts on a natural key, then clears the deletion marker and emits the event downstream consumers need.
- **Filters are separate and independently bypassable.** A database usually carries more than one default filter (soft delete, tenancy, authorization). A bypass removes only the filter it needs, and never the others.
- **Foreign references are logical, never physical, across apps.** A column holding another app's identifier has no database constraint, and the app tolerates "not found" when the identifier is resolved through the owning app's API.
- **Raw SQL is allowed only when there is no better option**, such as LINQ. Typed queries are the default, so a model change breaks the build. Where raw SQL is used, it is parameterized, never built by string concatenation, and carries a one-line comment saying why.
- **Lists are paginated with a stable order.** An unbounded query is allowed only in scheduled jobs over bounded data.
- **Avoid N+1 by design.** Read paths project to a read model. Cross-aggregate queries return projections, not entities, so aggregates do not couple through the data layer.
- **Events are written to the outbox in the same transaction as the state change**, never published directly from the service.
- **Constraints are the last line of defence, not the only one.** The same rule may be checked in the UI (friendly messages), in the service/domain (cross-aggregate and lookup-based rules) and in the database. The layers are deliberate, not redundant. However, there database constraints get complicated fast, so we limit it to the described constraints later in this document.
- **Tests run against the real database engine** (a container or the provider's emulator), never an in-memory or lighter stand-in.

## Units of work

- **Every use case is its own unit of work.** One entry point (a request, a message, a scheduled job) is one unit of work. If it fails before it commits, nothing is persisted.
- **A unit of work commits explicitly, exactly once**, in the use case. Nothing commits implicitly on its behalf (request filters, middleware, pipeline behaviors, disposal).
- **Only the entry-point use case commits.** Anything it calls (other services, helpers) stages its changes and does not commit, so the whole action stays atomic. There are no ambient or nested units of work.
- **A unit of work never shares its data-access context with another concurrent operation.** Parallel tasks, background work and other requests each get their own.

## Coded values (enums)

A persisted coded value (an enum, a status, a type code) is a contract with everything that can read the data: other apps, reports, queued events and API responses.

- **Coded values are stored as integers.** Each value has a fixed, explicit number that never changes meaning.
- **A stored value is never removed, renumbered or reused.** A retired value stays, marked obsolete. Removing one is allowed only after a data migration has rewritten every row, event and payload that could still hold it.
- **The model guards the values.** A number that is not a defined value is rejected where data enters the model, both when reading from storage and when accepting new input. The database is not the guard for this, so there is no `CHECK` constraint listing the members.
- **Same rule in every language and every storage form.** Events and API payloads carry a stable name for the value instead of its number, and the name follows the same rule: never renamed, removed or reused.
- **An open set is a lookup table**, not a coded value. Use one when the set carries metadata (display name, ordering, decimals) or is maintained by domain administrators at runtime (countries, currencies, product categories). The using table references it with a foreign key, and an explicit `sort_order` column is used when order matters.
- **A lookup table is per app.** A shared set (country codes, currencies, VAT rates) is seeded into each app's own database from one shared source file through migrations. A shared "reference" database is never used. Dynamic data that one app owns reaches the others through its events and a local read model.
- **One status, not several flags.** Several `BIT` columns (`is_open`, `is_paid`, `is_cancelled`) allow impossible states. Model one coded status instead.

## Relational databases

### Naming

- **Identifiers are lowercase snake_case** for tables, columns and constraints. The convention is configured once, not per object.
- **Tables are plural, columns are singular.** `customers` holds many, `email` holds one value per row.
- **No abbreviations** unless they are domain-canonical (`vat` yes, `cust` no), no Hungarian prefixes (`tbl_`, `c_`), and no reserved words as identifiers (`order`, `group`, `user`). Never rely on bracket-quoting.
- **Primary key column is always `id`.** A foreign key column is `<other_table_singular>_id`, with the role prepended when it is ambiguous (`billing_address_id`). Generic names (`parent_id`, `ref_id`) and columns named `data` or `meta` are not used.
- **Junction tables are named `<table_a>_<table_b>`, alphabetically** (`customers_tags`). A junction table with its own attributes becomes a first-class table with its own domain name (`assignments`).
- **Every constraint and index is named explicitly**, never auto-named, because generated names are cryptic and differ per environment, which breaks scripts that reference them.

  | Kind | Format | Example |
  |---|---|---|
  | Primary key | `pk_<table>` | `pk_customers` |
  | Foreign key | `fk_<table>_<column>` | `fk_orders_customer_id` |
  | Unique constraint | `uq_<table>_<columns>` | `uq_customers_email` |
  | Check constraint | `ck_<table>_<rule>` | `ck_orders_amount_positive` |
  | Default constraint | `df_<table>_<column>` | `df_orders_created_at` |
  | Index | `idx_<table>_<columns>` | `idx_orders_status_created_at` |
  | Filtered index | `idx_<table>_<columns>_where_<predicate>` | `idx_customers_email_where_active` |
  | Trigger | `trg_<table>_<event>` | `trg_bookings_no_overlap` |

- **Multi-column index names list the columns in the order of the index.**
- **One schema per app, named after the app** (`hello`, `billing`). The default `dbo` schema holds no application tables. A second schema (for example `<app>_archive`) is allowed only for a clear separate purpose such as cold-storage archive, auditing or staging tables. Cross-schema joins are not the default way of organizing tables.

### Keys and relationships

- **Every table has a primary key.** No exceptions: not "it is just a log table", not "rows are append-only". A key makes a row addressable (update and delete target exactly one row), referenceable, free of silent duplicates from retried inserts, and replicable row-for-row. A table without one is a defect that does not pass review.
- **The primary key is a synthetic `identifier`/`id`**, even when a natural unique value exists. A natural value (email, slug, external reference) becomes a `UNIQUE` constraint, never the key, because keys are immutable and natural values change. A natural key would also leak business meaning into every join and URL, and a wide composite one drags its width into every referencing table.
- **Junction tables and tuple-identified tables use a composite primary key.** The key of a junction table is the composite of its two foreign keys, with no `id` of its own. Any other table uses a composite key only when the tuple is the real identity (for example a per-period rollup keyed by `(account_id, period)`), never "for performance".
- **Foreign keys are mandatory within an app**, and always reference a primary key. If two tables are joined, a declared foreign key exists between them. If there is none, the relationship is not modelled yet: add the column and the constraint.
- **Joins run on declared keys**, child foreign key to parent primary key. Joining on a natural or text column (`email`, `name`, `slug`) is a defect: the value can change and silently detach rows, it has no integrity guarantee, it is usually not indexed, and it fans out when it is not unique.
- **`ON DELETE NO ACTION` is the default**, so the database refuses to delete a parent that still has dependents and ownership bugs surface. `CASCADE` is allowed only when the dependent cannot exist without the parent (order lines without their order, junction rows). `SET NULL` is allowed for optional references. A cascade is silent, so it is chosen with awareness and never applied everywhere.
- **Adding a foreign key to a large table is two steps.** First add it `WITH NOCHECK` (new writes only, no scan), then validate the existing rows in a later migration with `WITH CHECK CHECK CONSTRAINT`. Until then the constraint is untrusted and the optimizer ignores it, so an untrusted foreign key is never left behind.

### Data types

Take the default type unless the reason for deviating can be named.

| Domain concept | Type | Notes |
|---|---|---|
| Identifier | `UNIQUEIDENTIFIER`/`BINARY(16)` | App-generated `UNIQUEIDENTIFIER` for GUIDv4 and `BINARY(16)` for GUIDv7 |
| Short text | `NVARCHAR(n)` | With an honest bound that means something in the domain (320 for an email, 200 for a display name), never a reflexive 255 |
| Long text | `NVARCHAR(MAX)` | Only for genuinely long text. It can spill out-of-row and cannot be an index key |
| Whole number | `BIGINT` | Never `SMALLINT` "to save space" |
| Money | `DECIMAL(19, 4)` | Exact. Four decimals even for EUR |
| Other decimal | `DECIMAL(p, s)` | Explicit precision, with the reason documented |
| Boolean | `BIT` | Not three-valued: `NULL` meaning "unknown" is modelled as an explicit state |
| Timestamp | `DATETIMEOFFSET` | Always with offset, stored in UTC. Time zones are presentation |
| Date only | `DATE` | Only when the time of day is genuinely irrelevant |
| Duration | `BIGINT` | With the unit in the column name (`duration_seconds`) |
| JSON | `NVARCHAR(MAX)` | With an `ISJSON()` check constraint |
| List | Child table | There is no array type, and anything queryable deserves rows |
| Location | `GEOGRAPHY` / `GEOMETRY` | Geodetic / planar |
| Network address | `NVARCHAR(45)` | Normalised on write, 45 covers IPv6 |

- **Money is `DECIMAL`, never `FLOAT`, `REAL`, `MONEY` or `SMALLMONEY`.** Binary floats cannot represent `0.1`, and `MONEY` rounds surprisingly. Prices are not stored as integer cents.
- **One column, one currency.** A column that holds EUR in one row and USD in the next is wrong. Use one column per currency, or an amount plus an ISO 4217 `currency` column checked for consistency within an aggregate.
- **Text comparison semantics are explicit where uniqueness depends on them.** The collation of a column such as `email` is set on the column, so a change of the database default can never flip its case sensitivity.
- **Never `CHAR(n)` or `NCHAR(n)`.** They pad with spaces.
- **Never `DATETIME` or `DATETIME2` for instants.** Without an offset the stored moment shifts when a server changes time zone.
- **The T-SQL `TIMESTAMP` type is not a point in time.** It is a deprecated synonym for `ROWVERSION`, a row-change counter, used only as a concurrency token.
- **JSON is used sparingly.** A field that is queried, filtered on or constrained is promoted to a persisted computed column with a regular index, or becomes a real column. A "find rows whose document contains this fragment" query is an anti-pattern, because SQL Server has no general-purpose JSON index.
- **Never use** `TEXT`, `NTEXT`, `IMAGE`, `SQL_VARIANT`, `NVARCHAR` columns holding dates or numbers, `BIGINT` columns holding Unix timestamps, or comma-separated lists in a column (a child table instead).
- **Files do not live in the database.** The bytes go to blob storage, and the table stores the reference.

### Nullability and constraints

- **Nullability is a schema decision.** Columns are NOT NULL unless a stated reason says otherwise, and the reason is documented where the column is added. A nullable column is right when the value is genuinely absent for some rows (`archived_at`), is filled by a later workflow step (`paid_at`), or is an optional reference (`assigned_to`).
- **Business uniqueness is a `UNIQUE` constraint**, composite when needed, with both columns named in it (`uq_<table>_<column1>_<column2>`). With soft delete, uniqueness is a filtered unique index `WHERE deleted_at IS NULL`, so deleted rows may hold the same value and a restore conflict is caught at the domain level.
- **Soft delete is a nullable `deleted_at DATETIMEOFFSET`**, never an `is_deleted BIT`, because the timestamp also says when. It is a sibling of the audit columns, not one of them.
- **Cross-table consistency rules do not live in triggers.** Something like "`orders.total` equals the sum of its lines" is computed on read or denormalised explicitly.
- **Triggers are allowed but suspect.** Audit values, event emission and computed values each have a better home (the application, the outbox and computed columns). A trigger is short, named `trg_<table>_<event>`, and is never paired with application code doing the same job (a trigger-stamped `updated_at` next to an application-stamped one).
- **Exclusion rules (such as "no two bookings of a room overlap") are enforced in the writing transaction**, which is the primary guard: a range check with `UPDLOCK, HOLDLOCK` before the insert, with a supporting index on the filtered columns so the locked range stays narrow. An `AFTER INSERT, UPDATE` trigger that repeats the check is the backstop against writes that bypass the service path. The cost is real: writers on the same range serialize, so keep the transaction tiny and measure hot ranges.

### Audit columns

- **Every table has `created_at` and `updated_at`** (`DATETIMEOFFSET NOT NULL DEFAULT SYSUTCDATETIME()`), even when "we never update". Most tables also have `created_by` and `updated_by` (`UNIQUEIDENTIFIER`, nullable because migrations, scheduled jobs and queue-triggered functions have no user identity).
- **The database default is the safety net, and the application is the day-to-day path.** The default covers a hand-written insert or a data migration. The application sets `updated_at` on every save, because the default only fires on insert.
- **Raw SQL and bulk statements set `updated_at = SYSUTCDATETIME()` explicitly.** A trigger that stamps it is permitted but not the default, because it is one more object to maintain per table.
- **Audit columns use one naming convention across all tables.** There is no `createdAt` here and `inserted_at` there.
- **Not audit columns:** `created_via` / `updated_via` (the trace context holds that), a free-text `audit_note`, a `version` column (a concurrency token is its own column), and `deleted_at`.
- **Audit columns do not hold history.** They say who last touched a row and when, not what it looked like before. History comes from the outbox events, an application-level `audit_log` table (`actor`, `action`, `resource_id`, `payload`, `trace_id`, `at`) added when product or compliance asks, or temporal tables, which are not the default because of their ceremony.

### Indexes

- **The clustered index is the primary key.** A heap (a table without a clustered key) is a smell.
- **Index every foreign key.** SQL Server does not do it, and without one cascades and joins scan.
- **Index columns used in the `WHERE` of high-frequency queries**, and the `ORDER BY` of paginated lists, usually as the filter column followed by the sort column. Profile first, and do not add indexes "in case".
- **Do not index** low-cardinality columns that have no filtered or multicolumn role (a lone `BIT` or a 4-value `status`), columns that change often and are rarely filtered, or every column "to be safe".
- **Column order in a multicolumn index:** the most selective column first when it leads the `WHERE`, and the sort column last. A composite index serves prefix queries only (`(customer_id, created_at)` serves `customer_id` alone, not `created_at` alone).
- **Pick the type by query:** nonclustered for equality, range and sort on scalars; filtered for "active subset" predicates; a persisted computed column plus nonclustered for hot JSON fields; full-text for text search; columnstore only for analytical scans, never on OLTP hot paths.
- **Filtered indexes narrow the rows** (`WHERE deleted_at IS NULL`, unpublished outbox rows). They only take simple comparison predicates, writing to the table needs the ANSI `SET` options (`QUOTED_IDENTIFIER ON`), and the query predicate must match the index predicate. Keep the filter condition literal in the query, because a parameter can make the optimizer skip the index, and use `OPTION (RECOMPILE)` on drain-style queries where plan reuse fights the filter.
- **`INCLUDE` columns serve very hot read paths only**, because they inflate the index.
- **Computed columns are persisted before they are indexed.** A nondeterministic or non-persisted one cannot be.
- **Large insert-heavy tables that still fragment** get `FILLFACTOR = 90`. A nonclustered primary key with a different clustered key is a measured, deliberate deviation, never a scaffolding-time choice.
- **Indexes are removed when unused.** Zero seeks for a quarter in `sys.dm_db_index_usage_stats` makes it a drop candidate. An index is not re-created on every deploy with `DROP INDEX IF EXISTS`.
- **`ORDER BY NEWID()` has no index fix.** Use `TABLESAMPLE` or a pre-randomised column.

### Index maintenance

- **Rebuilding or reorganizing an index is a measured fix, not a routine ritual.** `sys.dm_db_index_physical_stats` finds fragmentation, and a rebuild is `ALTER INDEX ... REBUILD WITH (ONLINE = ON)` or `REORGANIZE`.

### Outbox table

Each app has its own `outbox` table (never shared across apps) that makes event emission transactional. It is part of the app's schema and migrations.

```sql
CREATE TABLE outbox (
    id UNIQUEIDENTIFIER NOT NULL CONSTRAINT pk_outbox PRIMARY KEY
    , aggregate_type VARCHAR(100) NOT NULL
    , aggregate_id UNIQUEIDENTIFIER NOT NULL
    , topic VARCHAR(200) NOT NULL
    , event_type VARCHAR(100) NOT NULL
    , schema_version INT NOT NULL
    , payload NVARCHAR(MAX) NOT NULL
    , created_at DATETIMEOFFSET NOT NULL DEFAULT SYSUTCDATETIME()
    , published_at DATETIMEOFFSET
    , CONSTRAINT ck_outbox_schema_version_positive CHECK (schema_version > 0)
    , CONSTRAINT ck_outbox_payload_json CHECK (ISJSON(payload) = 1)
);

CREATE INDEX idx_outbox_unpublished
    ON outbox (created_at)
    WHERE published_at IS NULL;
```

- **The row `id` is the event id** that subscribers deduplicate on. It is generated by the application, so it is known before the insert.
- **The filtered index on unpublished rows is mandatory.** It keeps the index the size of the backlog, not of the history. The drain query keeps `published_at IS NULL` literal.
- **`aggregate_id` has no foreign key.** Outbox rows outlive their aggregate (the `deleted` event still publishes), and several aggregate types share the column.
- **A published row is marked with `published_at`, never deleted on publish.** A failed publish leaves it null, and the next drain picks it up. Ordering is by `created_at`, without aggregate-scoped sequence numbers, unless an app needs strict per-aggregate order that this does not deliver.
- **The drain claims small batches** (`TOP (100)`, tunable per app) with `UPDLOCK, READPAST, ROWLOCK`, so concurrent drains skip each other's rows. Large batches invite lock escalation to a table lock, which defeats `READPAST`.
- **A janitor removes published rows in chunks** (`DELETE TOP (5000)`, looped), after a retention period that is configurable per app. The default is 30 days and the floor is 7 days, never hard-coded.
- **Outbox columns are not renamed**, because the platform events library reads them by name. Adding a column is forward-compatible.

### Transactions and bulk operations

- **One unit of work is one transaction.** The idempotency claim (api.md) is the one exception: it commits on its own, before the unit of work. Any other second explicit transaction inside one use case is a design question first.
- **Paging uses an explicit order on a stable key** before skipping and taking.
- **Bulk operations bypass the application's audit and event hooks.** They set audit values explicitly, and are never used when they would skip an aggregate invariant or an outbox event.

### Schema changes (migrations)

- **One change per migration.** The rule is about intent, not statement count: a table with its indexes and initial seed is one change. Reviewability, forward fixability and failure isolation are the reasons.
- **Migrations are immutable once merged to `main`.** A mistake is fixed with a new forward migration, never by editing a deployed one, its timestamp or its history record, and never by rewriting history. A table is never dropped and re-created as a "fix".
- **Up-only.** Rollback is a corrective forward migration.
- **Review the SQL, not just the generating code.** Every migration PR includes the generated SQL of the new migration, because a builder API hides the real DDL and the occasional destructive rename.
- **A migration is backward compatible.** The previous release runs side by side with the new one during a deploy and must keep working against the new schema.

  | Change | Safe shape |
  |---|---|
  | Add nullable column | Safe, old code ignores it |
  | Add NOT NULL column with a default | Safe, metadata-only on Azure SQL for runtime-constant defaults |
  | Add NOT NULL column without a default | Unsafe. Add nullable and backfill, then make it NOT NULL in a later migration |
  | Drop column | Stop reading it in one release, drop it in the next |
  | Rename column, change column type | Add the new column, dual-write, then drop the old one, across releases. Never a rename in one migration |
  | Add unique constraint | Safe if the data already obeys it, otherwise after the backfill |
  | Add foreign key | On a large table: `WITH NOCHECK`, then re-check in a later migration |

- **Large tables (over about 1M rows) never take long locks.** Indexes are built `WITH (ONLINE = ON)`, outside the migration transaction, because an online build inside a long transaction holds its locks to the end. A resumable build can be left paused, so the next deploy detects and resumes or aborts it. A new index on a large table is allowed in a migration only this way.
- **Views, functions and procedures are defined idempotently** (`CREATE OR ALTER`) in a migration of their own. A change is a new migration with the full current definition, never mixed with table changes.
- **Backfills are application work, not migrations.** The migration adds the column, and a background worker fills it in chunks (`UPDATE TOP (10000)`), so a long backfill never stalls the deploy gate.
- **Seed data:** reference data (countries, currencies, VAT rates) goes through migrations. Demo and test data never ship in production migrations, and live in a separate script set loaded only in local and acceptance.
- **Migrations are environment-agnostic.** No logic that depends on the environment.
- **The pipeline applies migrations, not the app.** They run as a gate before traffic shifts, from the same commit as the app, so a failed migration aborts the deploy and the schema the code expects cannot drift from the schema the migrations produce. No app applies migrations on startup, because instances would race each other.
- **No destructive reset (drop database) in a pipeline.**
- **An integration test applies all migrations to a fresh database** and checks that the model has no unmigrated changes.
- **Testing Migrations.** Migrations are rehearsed on a local copy or synthetic dataset provided, never on actual databases in the cloud.

## Document databases (Cosmos DB)

- **One aggregate is one document.** The partition key is chosen deliberately and documented per container. This is the aggregate-boundary rule made physical.
- **Child entities that only exist inside the aggregate are embedded.** Other aggregates are referenced by ID, never embedded.
- **A save is atomic only within one partition.** A use case never changes aggregates in different partitions in one save, and an outbox entry lives in the same partition as the state change it belongs to.
- **Queries are cost-aware (request units).** Avoid cross-partition queries on hot paths, and project only the properties needed.
- **There are no migrations.** The schema evolves through a `schemaVersion` property on documents, with reads tolerant of older shapes and an upgrade done lazily on write or by a background job.
- **Containers and indexing policy come from infrastructure-as-code.**
- **Bulk changes are background jobs over partitions**, since bulk update and delete are not available.

## Security

- **Queries are parameterized or typed.** Never build SQL by concatenating or formatting input into a string. Where raw SQL is unavoidable it uses the parameterized forms and carries a one-line reason.
- **The application connects with its own least-privilege identity.** No shared accounts, no administrator credentials in application settings.
- **Tenant and authorization filters stay on.** A bypass removes only the single filter it needs, never all of them. Bypass paths are named, intent-revealing and tested.
- **Verbose database logging is off outside the Local environment.** Sensitive-data logging and detailed errors write parameter values (personal data) into logs.
- **(GDPR) Personal and confidential columns are identified** and have a defined retention period and an erasure path. Soft delete is not erasure.
